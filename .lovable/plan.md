## نتيجة الفحص الحالي

- **حالة النشر:** المشروع منشور فعلاً، والرابط العام يعمل، والرؤية `public`.
- **الدومين المخصص:** `waqf-wise.net` يستجيب ويعرض الصفحة المنشورة.
- **Lovable Cloud - Live:** الخلفية الحية تعمل بشكل طبيعي.
- **Lovable Cloud - Test:** الخلفية الاختبارية تعمل عند فحص `test`، لكن فحص `development` أعاد خطأ صلاحيات للواجهة الداخلية؛ هذا قد يفسّر فشل زر النشر إذا كان يستخدم قناة بيئة مختلفة أو صلاحية نشر غير متاحة مؤقتاً.
- **سجلات آخر ساعتين:** لا توجد أخطاء حديثة في قاعدة البيانات أو المصادقة أو وظائف الخلفية.
- **فحص الأمان:** يوجد عدد كبير من تحذيرات/أخطاء linter الآلية، أهمها:
  - وجود View أو أكثر بنمط Security Definer حسب الفاحص.
  - دوال `SECURITY DEFINER` قابلة للتنفيذ من `anon`، وهذا خطر أمني ويجب تضييقه.
  - تحذير حول bucket عام يسمح بالاستعراض، مع ملاحظة أن ذاكرة المشروع تقول إن `waqf-assets` عام عمداً لأصول PDF والبريد.
- **مؤشرات ليست سبباً مباشراً لفشل النشر:** لا يوجد دليل من الفحص أن الكود نفسه يمنع الوصول للرابط المنشور، ولا توجد أخطاء runtime ظاهرة في السجلات.

## خطة التنفيذ المقترحة بعد موافقتك

### 1. عزل سبب فشل النشر
- مراجعة إعدادات النشر والبيئات مرة أخرى بعد محاولة نشر جديدة مباشرة.
- فحص حالة Live وTest فقط، وتجنب الاعتماد على اسم بيئة يعيد خطأ صلاحيات داخلي.
- مقارنة استجابة الرابط المنشور مع أحدث إصدار في Preview لتحديد هل الفشل في عملية deploy نفسها أم في مزامنة Cloud.

### 2. معالجة مخاطر قاعدة البيانات التي قد تعطل النشر أو تولد رفضاً أمنياً
- استخراج قائمة دقيقة بأسماء الدوال العامة `SECURITY DEFINER` القابلة للتنفيذ من `anon`.
- تصنيفها إلى:
  - دوال داخلية/Triggers/Cron لا يجب أن يستدعيها anon.
  - دوال RPC يحتاجها المستخدمون المصادقون فقط.
  - دوال عامة مقصودة إن وجدت.
- إنشاء migration واحد يطبق `REVOKE EXECUTE FROM anon` على الدوال غير العامة فقط، مع الإبقاء على `authenticated`/`service_role` حسب الحاجة.
- عدم تغيير الدوال الحساسة أو سياسات RLS بدون مطابقة استخدامها في الكود.

### 3. التعامل مع Security Definer Views بدون كسر حماية PII
- تحديد أسماء الـ views التي يراها الفاحص كـ Security Definer.
- احترام ذاكرة المشروع: `contracts_safe` مقصود لإخفاء PII وممنوع تحويله عشوائياً.
- لأي view آخر غير مقصود: تحويله أو تضييق صلاحياته بطريقة لا تكسر الصفحات.
- إذا كانت النتائج false-positive أو مقصودة، توثيق الاستثناء في security memory بدلاً من تغيير أمني خطير.

### 4. مراجعة bucket العام
- تأكيد هل التحذير يخص `waqf-assets` فقط.
- إن كان `waqf-assets`: توثيق أنه عام عمداً لأصول PDF والبريد كما في ذاكرة المشروع.
- إن شمل bucket آخر مثل invoices أو disbursement-vouchers: تضييق سياسة القراءة فوراً لأنها ملفات حساسة.

### 5. التحقق بعد الإصلاح
- تشغيل linter/security scan بعد migration.
- إعادة فحص سجلات Live/Test.
- اختبار الرابط المنشور والدومين.
- إذا ظل زر النشر يفشل رغم سلامة الكود والخلفية، فالسبب غالباً صلاحيات/خدمة نشر في Lovable وليس من المشروع، وسأعطيك تقريراً مختصراً بما ترسله للدعم.

## ملاحظة مهمة

لن أطبق migration الآن لأننا في وضع الخطة فقط، ولأن بعض تحذيرات الأمان قد تكون مقصودة في هذا المشروع وتحتاج تصنيفاً قبل أي تغيير.
